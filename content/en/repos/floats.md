# floats {#floats}

[![CI](https://github.com/go-simd/floats/actions/workflows/ci.yml/badge.svg)](https://github.com/go-simd/floats/actions/workflows/ci.yml)
![coverage](https://img.shields.io/badge/coverage-100%25-brightgreen)

SIMD-accelerated reductions over `[]float32` **and** `[]float64` — the dot
product, sum, min, max, Euclidean (L2) distance and cosine similarity that sit at
the heart of **vector search, embeddings and numerics**. Pure Go
(`CGO_ENABLED=0`, stable Go, no `GOEXPERIMENT`). The hot reduction loops are real
FMA SIMD on **all six** of Go's 64-bit targets, assembly generated by
[go-asmgen](https://github.com/go-asmgen/asmgen).
[Repository →](https://github.com/go-simd/floats)

## API {#api}

For `[]float64` (top-level) and `[]float32` (the `Float32*` functions):

| float64 | float32 | meaning |
|---|---|---|
| `Dot(a, b)`              | `Float32Dot(a, b)`                | a·b = Σ aᵢbᵢ |
| `Sum(a)`                 | `Float32Sum(a)`                   | Σ aᵢ |
| `Min(a)` / `Max(a)`      | `Float32Min(a)` / `Float32Max(a)` | min / max (NaN-propagating) |
| `Distance(a, b)`         | `Float32Distance(a, b)`           | ‖a−b‖₂ = √Σ(aᵢ−bᵢ)² |
| `CosineSimilarity(a, b)` | `Float32CosineSimilarity(a, b)`   | a·b / (‖a‖₂‖b‖₂) |

```go
import "github.com/go-simd/floats"

sim := floats.CosineSimilarity(query, doc)  // []float64 relevance score
d   := floats.Float32Distance(embA, embB)   // []float32 L2 distance
dp  := floats.Dot(a, b)                      // a·b
```

`Dot`, `Distance`, `CosineSimilarity` require `len(a) == len(b)` and panic
otherwise; `Min`/`Max` panic on an empty slice; `Sum` of empty is 0. The float32
dot/sum/squared-difference accumulate in float32; cosine and distance take the
final square root in float64 for accuracy.

## Elementwise updates (BLAS level 1) {#elementwise-updates}

Since v0.4.0, the float64 in-place updates behind iterative solvers (CG, GMRES),
Householder QR and LU elimination:

| function | computes |
|---|---|
| `Axpy(alpha, x, y)`       | `y[i] = math.FMA(alpha, x[i], y[i])` (y += αx) |
| `Xpby(x, beta, y)`        | `y[i] = math.FMA(beta, y[i], x[i])` (y = x + βy) |
| `AxpyDot(alpha, x, y, w)` | Axpy, then returns Σ `y[i]*w[i]` over the updated y, in one pass |
| `Scale(alpha, x)`         | `x[i] *= alpha` |

```go
// one conjugate-gradient step
floats.Axpy(alpha, p, x)               // x += αp
rr := floats.AxpyDot(-alpha, ap, r, r) // r -= αAp, rr = r·r
floats.Xpby(r, rr/rrOld, p)            // p = r + βp
```

They operate on the first `len(x)` elements and panic if `y` (or `w`) is
shorter; `y` may be the same slice as `x` or `w`. The updated slices are
**bit-identical to `math.FMA` on every architecture**: one rounding per element,
via `VFMADD` (amd64 AVX2+FMA), `VFMLA`/`FMADDD` (arm64 NEON) or the portable
`math.FMA` loop (ppc64le, s390x, riscv64, loong64, where no kernel has been
measured on silicon yet). `AxpyDot`'s returned sum is a lane-blocked reduction,
like `Dot`.

Speedup over the hand-written scalar loop (`y[i] += alpha*x[i]`, …), single
core, median of 3:

| op | n = 1e3 / 1e5 / 1e6, Apple M4 Max | AMD EPYC 7763 |
|---|---|---|
| `Axpy`    | 2.06× / 1.74× / 1.66× | 5.25× / 3.12× / 3.14× |
| `Xpby`    | 2.01× / 1.58× / 1.65× | 5.25× / 3.10× / 3.14× |
| `AxpyDot` | 5.30× / 4.85× / 2.91× | 5.85× / 3.03× / 3.14× |
| `Scale`   | 3.57× / 2.23× / 2.22× | 7.67× / 5.25× / 5.80× |

## Gather kernels (index list) {#gather}

Since v0.17.0, the free-set operations of bound-constrained solvers (L-BFGS-B
subspace minimisation, active-set QP): vectors read through a list of active
indices.

| function | computes |
|---|---|
| `DotIdx(a, b, idx)`            | Σₖ `a[idx[k]]*b[idx[k]]` |
| `DotGather(a, idx, d)`         | Σₖ `a[idx[k]]*d[k]` (`d` contiguous, `a` gathered) |
| `AxpyGather(alpha, a, idx, d)` | `d[k] = math.FMA(alpha, a[idx[k]], d[k])` for every k |

Portable Go for now (no assembly; a SIMD gather can replace it behind the same
signatures). They panic if an index is out of range or `len(d) < len(idx)`;
repeated and unordered indices are allowed.

**Accuracy contract.** The two sums use four FMA accumulators over lane-blocked
groups of four indices, combined as `(s0+s1)+(s2+s3)`: they are **not** summed
left to right, so the last bit differs from the obvious loop. The stated bound,
asserted against a 300-bit `math/big` oracle, is |result − exact| ≤
n·ε·Σₖ|aᵢbᵢ| with ε = 2⁻⁵² (plus an absolute 2⁻¹⁰⁷⁴ term per element when
products underflow to subnormals). `AxpyGather` rounds each element once and is
bit-identical on every architecture.

## Products, combinations, clamping, infinity norm {#qp-kernels}

Since v0.5.0, the vector kernels of splitting solvers (ADMM / OSQP-style
quadratic programming):

| function | computes |
|---|---|
| `Mul(dst, a, b)`                           | `dst[i] = a[i]*b[i]` |
| `Axpby3(dst, alpha, a, beta, b, gamma, c)` | `dst[i] = math.FMA(gamma, c[i], math.FMA(beta, b[i], alpha*a[i]))` (αa + βb + γc, fused) |
| `Clamp(dst, v, lo, hi)`                    | `dst[i] = min(max(v[i], lo[i]), hi[i])` with the exact rules below |
| `MaxAbs(v)`                                | the largest `abs(v[i])` (∞-norm); 0 for an empty slice |
| `MaxAbsMul(v, w)` (since v0.25.0)          | `max(abs(v[i])*w[i])`, the weighted max-norm of ODE error control, folded with C's `fmax` from +0 (a NaN product loses), bit-identical to that loop; NEON on arm64, AVX2 on amd64, portable loop elsewhere; 0.17–0.43 of NumPy's time (arm64, one core) |

```go
floats.Axpby3(t, alpha, ax, 1-alpha, zPrev, 1, yOverRho)
floats.Clamp(z, t, l, u)
rNorm := floats.MaxAbs(r)
```

They work on the first `len(a)` (`len(v)`) elements, panic if another slice is
shorter and let `dst` alias an input. **Bit-identical on every architecture**
(NaN payloads of arithmetic results aside): `Mul` is one IEEE multiply;
`Axpby3` is fused, so it differs from the unfused expression by a few ULP of
`Σ|terms|`; `Clamp` and `MaxAbs` round nothing.

`Clamp` is `r := v; if lo > r { r = lo }; if hi < r { r = hi }`: a NaN `v`
passes through with its own bits (either sign), a NaN bound is ignored,
`lo > hi` gives `hi`, signed zeros tie. `MaxAbs` returns `math.NaN()` if any
element is NaN (either sign, quiet or signaling), `+Inf` if there is an
infinity and no NaN, and `+0` for an all-zero slice.

Kernels: AVX2+FMA on amd64 (`VMULPD`, `VFMADD231PD`, `VMAXPD`/`VMINPD`,
`VANDPD` plus an unordered-compare NaN mask), NEON on arm64 (`VFMUL`, `VFMLA`,
`VFCMGT`+`VBIT`, `VFABS`+`VFMAX`), the portable loops on ppc64le, s390x,
riscv64 and loong64. Tested for every length 0..257 at four offsets with
planted negative and signaling NaNs and signed zeros, at every position of
0..67, with guard pages and fuzzing, at 100% coverage on amd64 and arm64.

Against NumPy 2.5.4 (`bench/numpycmp` in the repository; M4 Max, one core,
median ns/op of 9 interleaved rounds, measured 2026-11-01 at 1-minute load 2.7;
the tool refuses to run at a load of 8 or above):

| `Mul`    | 1e3 | 104 | 324 | 269 | 3.12× | 2.59× |

| `Mul`    | 1e6 | 198 848 | 294 678 | 195 000 | 1.48× | 0.98× |

## Elementwise `Add`, `Sub`, `Div`, `Sqrt`, `ClampScalar` {#binop}

Since v0.8.0:

| function | computes |
|---|---|
| `Add(dst, a, b)` / `Sub(dst, a, b)` / `Div(dst, a, b)` | `dst[i] = a[i] + b[i]` / `a[i] - b[i]` / `a[i] / b[i]` |
| `Sqrt(dst, src)` | `dst[i] = math.Sqrt(src[i])` |
| `ClampScalar(dst, v, lo, hi)` | `dst[i] = min(max(v[i], lo), hi)` with `Clamp`'s exact NaN and signed-zero rules and scalar bounds (`np.clip(v, lo, hi)`) |

These are the float64 elementwise kernels go-ndarray kept privately (K1 of the
go-scikit performance campaign: a kernel lives once, in the lowest library every
user can import). Each element is one IEEE operation or a comparison, never a
fused instruction, so the results are **bit-identical to the scalar Go loop and
to NumPy** (`np.add`, `np.subtract`, `np.divide`, `np.sqrt`, `np.clip`) on every
architecture. amd64 (AVX2, the usual gate) runs `VADDPD`, `VSUBPD`, `VDIVPD` and
`VSQRTPD`; arm64 NEON runs `VFADD`, `VFSUB`, `VFDIV` and `VFSQRT`; both are ×4
unrolled and generated by go-asmgen. The other architectures run the portable
loops. Like `Mul` they work on the first `len(a)` elements, panic if another
slice is shorter, allow `dst` to alias an input, and never read or write past a
slice (guard-page tests). Timing against NumPy is deferred: the benchmark module
(`bench/perf`, refbench) records allocation counts until the host's load allows a
measurement.

### float32 siblings (since v0.30.0) {#binop32}

`Add32(dst, a, b)`, `Sub32`, `Mul32`, `Div32` and `Sqrt32(dst, src)` are the same
five operations on `[]float32` (the SSE2 copies go-ndarray kept privately). One
IEEE binary32 operation per lane, so the result is the exact correctly rounded
one and bit-identical to the scalar loop; `Sqrt32` is
`float32(math.Sqrt(float64(x)))`. amd64 runs AVX2 (32 elements per iteration,
the usual gate) with an SSE2 baseline, arm64 runs NEON (`.S4`). Since v0.32.0
loong64 (LSX), ppc64le (VSX), riscv64 (RVV 1.0) and s390x (VXE, z14 and later)
run kernels too, ported exactly from go-ndarray's; they are verified under QEMU
(correctness, not timings) and **unmeasured on hardware**. All are generated by
go-asmgen and regenerated and diffed in CI. The length rules are those of the
float64 binops above. `Sqrt32` is checked over all 2^32 inputs against an oracle
that uses no square root, on the SSE2, AVX2 and NEON kernels; on the four
emulated architectures every 1021st pattern (about 4.2 million) plus the special
values. The NumPy timing rows are deferred (host load was 36 to 45);
`go test -bench Binop32` times each kernel against the scalar loop.

## Unfused, NumPy-exact updates {#nofma}

Since v0.7.0:

| function | computes (NumPy expression) |
|---|---|
| `AxpyNoFMA(alpha, x, y)` | `y[i] = y[i] + alpha*x[i]` |
| `XpbyNoFMA(x, beta, y)` | `y[i] = x[i] + beta*y[i]` |
| `Axpby3NoFMA(dst, alpha, a, beta, b, gamma, c)` | `alpha*a[i] + beta*b[i] + gamma*c[i]`, left to right |
| `AxpyDiffNoFMA(dst, a, f, b, c)` | `a[i] + f*(b[i] - c[i])`, the differential-evolution mutation |

`Axpy`, `Xpby` and `Axpby3` are fused (one rounding), which NumPy never is:
`y + alpha*x` is a multiply that rounds into a temporary and an add that rounds
again. A solver validated by exact equality against SciPy needs that path, so
these kernels round every product and every sum on its own, in the order NumPy
evaluates the temporaries, and are bit-identical to the NumPy expression on
every architecture (the payload of a NaN created by `Inf - Inf` or `0*Inf`
aside). amd64 uses `VMULPD`/`VADDPD`/`VSUBPD`, arm64 `VFMUL`/`VFADD`/`VFSUB`;
the portable code puts every product behind a `float64(...)` conversion, which
keeps the Go compiler from fusing it. `dst` may be the slice of an input
(`AxpyDiffNoFMA(b, b, f, x, b)` is `b += f*(x - b)`).

Validated against NumPy 2.5.4 on 13 088 committed fixture cases (four kernels,
ten value families including ±0, ±Inf, NaN of both signs and cancellation in
`b - c`, every length 0..300 and block boundaries): 0 mismatches on arm64 and
amd64. A planted fused variant and planted reordered variants are caught by the
same fixture. Speedups over NumPy are not published yet: the benchmark
(`bench/numpycmp`) refuses to run at a machine load of 8 or above.

## Reproducing `np.sum`: `SumPairwise` {#sum-pairwise}

Since v0.6.0:

| function | computes |
|---|---|
| `SumPairwise(a)` | `Σ a[i]`, **bit-identical to `np.sum(a)`** for a contiguous 1-D float64 array; `+0` for an empty slice |

`Sum` adds in the lane order of the SIMD kernels, which is fast but not NumPy's
order, so its last bits differ from `np.sum`. Use `SumPairwise` when a result
must be reproducible against NumPy, for example a stopping test comparing
`np.std` of a population with a tolerance. It is NumPy's pairwise summation,
transcribed from `DOUBLE_pairwise_sum` (`numpy/_core/src/umath/loops_utils.h.src`,
v2.5.3): fewer than 8 elements are added left to right from `-0`; up to 128
elements are summed with eight independent accumulators folded as
`((r0+r1)+(r2+r3)) + ((r4+r5)+(r6+r7))`, then the non-multiple-of-8 rest is
added one by one; a longer block is split at `n/2` rounded down to a multiple of
8. `np.add.reduce` adds the result to its initial `+0`, so a slice holding only
`-0` sums to `+0`, as in NumPy.

It is **bit-identical on every architecture**: the order is fixed in the code,
not by the width of a vector register, and no step is a fused multiply-add.
Since v0.7.0 the 8..128-element blocks run in SIMD on amd64 (AVX2: the eight
accumulators `r[0..7]` are two 4-lane registers) and arm64 (NEON: four 2-lane
registers); every lane receives exactly the additions NumPy's scalar code
performs on its `r[j]`, so the bits do not change. Other architectures run the
portable Go block, which is also the test reference for the SIMD blocks.

Validated against NumPy 2.5.4 on 6 990 committed fixture cases (every length
0..300 for nine value families, both sides of every block boundary
`128·2^j ± 12`, and 1e5 / 1e6 / 2^20 with odd lengths): 0 mismatches. A NaN
result is compared bit for bit when exactly one NaN enters the sum and the
hardware keeps NaN payloads (RISC-V returns the canonical NaN, so only "is NaN"
is compared there); with several NaNs, which one comes out is hardware-dependent
in NumPy too. `FuzzSumPairwise` checks against an independent transcription;
100% coverage on every CI lane.

## Lapped-transform and spectrum passes (v0.18.0 to v0.28.0) {#transform-passes}

Float64 kernels for the passes around an FFT in audio codecs and spectral
analysis (go-fft, go-avkit). Each is generated by go-asmgen for arm64 NEON and
amd64 AVX2(+FMA); the portable loop runs elsewhere and on an amd64 CPU without
AVX2+FMA. Where a contract is "a bound", it is asserted against a 200-bit or
300-bit computation, not against another float64 code.

|---|---|---|---|

| `MDCTFold(dst, x)`, `MDCTUnfold(dst, u)` and `MDCTFoldFrom32`, `MDCTUnfoldTo32` | v0.19.0 | the fold and unfold around the twiddle passes of an MDCT and an IMDCT | exact: one addition, subtraction or negation per output; `dst` must not overlap its operand (checked, panics) |
| `SquaredMagnitude(dst, c, s)` | v0.20.0 | `dst[k] = (c[2k]² + c[2k+1]²)·s` over `(re, im)` pairs: the power pass of a PSD or spectrogram | within 4 units of the last place of the exact value |
| `ConjReverse(dst, src)` | v0.21.0 | the conjugate mirror `X[N-k] = conj(X[k])` that turns the bins of a real transform into the full spectrum | exact (copies and negations); `len(dst)` must be even |

## Elementwise `Abs`, `Neg`, `Square`, `Floor`, `Ceil`, `Trunc`, `RoundEven` {#unary}

Since v0.23.0 (float64, `dst[i] = f(src[i])`):

| function | computes | NumPy |
|---|---|---|
| `Abs(dst, src)` | `math.Abs(src[i])` | `np.abs` |
| `Neg(dst, src)` | `-src[i]` | `np.negative` |
| `Square(dst, src)` | `src[i] * src[i]` | `np.square` |
| `Floor(dst, src)` | `math.Floor(src[i])` | `np.floor` |
| `Ceil(dst, src)` | `math.Ceil(src[i])` | `np.ceil` |
| `Trunc(dst, src)` | `math.Trunc(src[i])` | `np.trunc` |
| `RoundEven(dst, src)` | `math.RoundToEven(src[i])`, halfway to even | `np.rint`, `np.round` |

The operations go-ndarray still ran as scalar Go loops (go-ndarray/ndarray#118).
Each is **exact**: the result is the Go expression's, bit for bit, on every input
and every architecture (`±0` keep their sign, `±Inf` and `|x| ≥ 2⁵²` pass
through, subnormals are handled, a NaN stays a NaN). `Abs` and `Neg` only touch
the sign bit, so every NaN keeps its exact bits; for the others a signalling NaN
may come back quieted. Like `Sqrt` they work on the first `len(src)` elements,
panic if `len(dst) < len(src)` and allow `dst` to be `src` (exact overlap only).

Kernels: AVX2 (`VANDPD`/`VXORPD`, `VMULPD`, `VROUNDPD`), SSE2 for `Abs`, `Neg`
and `Square` on amd64 without AVX2+FMA, NEON, VSX, the s390x vector facility and
LASX; riscv64 RVV for `Abs`, `Neg` and `Square`. **The four rounding functions
stay scalar on riscv64** (RVV 1.0 has no vector round-to-integral instruction)
**and on amd64 without AVX2** (SSE2 has no `ROUNDPD`). One Zen 3 core, the AVX2
kernel against the scalar Go loop, 1e5 float64: 2.7 to 3.6× (23 µs for every
op: bound by the cache), and 6.2× (`Abs`) to 10.7× (`Ceil`; `RoundEven` 10.6×) at 1e3. Not yet timed against NumPy;
the other architectures were verified for correctness only (QEMU).

## Pairwise `Maximum`, `Minimum` {#pairwise}

Since v0.26.0 (float64):

| function | computes | NumPy |
|---|---|---|
| `Maximum(dst, a, b)` | `dst[i] = max(a[i], b[i])` (the Go builtin) | `np.maximum` |
| `Minimum(dst, a, b)` | `dst[i] = min(a[i], b[i])` (the Go builtin) | `np.minimum` |

The contract is the language's rule, the same on every kernel, bit for bit:

- **NaN**: a NaN in either operand gives that NaN unchanged (a signalling NaN
  stays signalling); two NaNs give `b[i]`.
- **Zeros**: `max(-0, +0)` and `max(+0, -0)` are `+0`, `min` of them is `-0`,
  whatever the operand order. (NumPy returns `a` when `a >= b`; this does not.)
- Otherwise the larger (smaller) operand.

Bit-identical to the builtin for numbers and zeros on every target. The README
documents one difference from the compiled scalar loop: the payload of a NaN
result can differ from the compiler's own `max` on arm64 and amd64, because the
compiler lowers it with the target's own NaN choice. Same shape as `Add`: the
first `len(a)` elements, a panic if `b` or `dst` is shorter, `dst` may be `a` or
`b`; no float32 variant.

Kernels: AVX2 and SSE2 (`VCMPPD` and blends), NEON (`FMAX`/`FMIN` plus a NaN
fix-up), VSX, the s390x vector facility, LASX and RVV; where none runs, the
builtin loop itself. One Zen 3 core, the AVX2 kernel against the compiled scalar
loop: `Maximum` 5.0× at 1e3 and 3.0× at 1e5, `Minimum` 3.9× and 2.0×. Not yet
timed against NumPy.

## Why this library {#why-this-library}

This is the **only** pure-Go float reduction library that ships the full
vector-search API (dot / Euclidean / cosine) for **both** float32 and float64 on
**all six** of Go's 64-bit SIMD architectures:

| | dot/dist/cosine | float32 | amd64 | arm64 | ppc64le / s390x / riscv64 / loong64 |
|---|---|---|---|---|---|
| gonum/floats   | dot, L2 only            | ✗ | SSE        | ✗    | ✗ |
| viterin/vek    | ✓                       | ✓ | AVX2+FMA   | ✗    | ✗ |
| kelindar/simd  | ✗ (sum/min/max only)    | ✓ | AVX2       | NEON | ✗ |
| **go-simd/floats** | **✓**               | **✓** | **AVX2+FMA** | **NEON** | **✓ (all four)** |

## Algorithm & per-arch kernels {#algorithm-per-arch-kernels}

Every kernel is an FMA-based vectorised reduction: a multi-lane accumulator
folded with a fused multiply-add at the vector stride, then a horizontal reduce
and a scalar tail.

| arch | ISA | FMA op | notes |
|---|---|---|---|
| amd64   | AVX2 + FMA3 | `VFMADD231P{S,D}` | 8 independent accumulators (since v0.35.0); gated on `cpu.X86.HasAVX2 && HasFMA`; scalar fallback otherwise |
| arm64   | NEON | `VFMLA` | 8 accumulators for the reductions (since v0.38.0), ×4 unroll for ILP elsewhere; baseline |
| riscv64 | RVV  | `VFMUL`+`VFREDOSUMVS` | length-agnostic `VSETVLI` stripmining; gated on `cpu.RISCV64.HasV` |
| s390x   | vector facility (**big-endian**) | `VFMADB`, `VFMASB` | 8 accumulators (since v0.35.0); float64 from 16 elements; float32 kernels use the z14 `.SB` ops emitted as encoded words, gated on the vector-enhancements facility (lane-blocked fallback); z13 baseline for float64 |
| ppc64le | VSX | `XVMADDADP`, `XVMADDASP` | XV* ops `WORD`-encoded; 8 accumulators for float64 (from 16 elements) and float32 since v0.35.0; gated on POWER8+ |
| loong64 | LSX  | `vfmadd.d`/`vfmadd.s` | LSX FP ops `WORD`-encoded; LA464 baseline |

Since v0.35.0 the reductions (`Dot`, `Sum`, `SumSqDiff`/`Distance` and the
float32 forms) keep eight independent accumulators on amd64, ppc64le and s390x,
so the FMA/add latency no longer bounds them; arm64 follows since v0.38.0
(loong64 and riscv64 are tracked in go-simd/floats#84). On arm64 (Neoverse,
base/new time ratio) n=1000 Sum 3.4×, Distance 1.7×, Float32Sum 3.1×; `Dot` is
load-bound and unchanged. Since v0.38.0 ppc64le and s390x also run 4 to 15
elements (below the vector threshold) through a four-accumulator scalar loop:
POWER9 n=12 Sum 21.5 to 13.4 ns, z17 n=12 Dot 11.8 to 7.4 ns. Single core, old to new: Zen 4
n=1000 Dot 3.2×, Sum 4.3×; POWER9 n=1000 Sum 934 to 281 ns, Float32Sum 596 to
251 ns; z17 n=1000 Sum 624 to 106 ns, Float32Sum 2898 to 61 ns (float32 was the
scalar reference there). The contract is an error bound against a 512-bit
`math/big` oracle, not bit equality. `Add32`/`Sub32`/`Mul32` use the SSE2 kernel
from 65536 elements on amd64 (7–10 % faster once memory-bound on Zen 3).

## Floating-point determinism {#floating-point-determinism}

A SIMD reduction does not add terms left-to-right: it keeps several independent
accumulator lanes (for ILP) and folds them at the end, so its rounding differs
from a naïve scalar loop. For dot / distance / cosine, bit-exactness against a
naïve loop is neither meaningful nor required — correctness to a few ULP is. The
reference the tests and fuzzers check against (`dotLanes`, `sumSqDiffLanes`, …)
reduces in the **same lane-blocked order** the kernels use, and each kernel must
match it to a tight, documented tolerance (`1e-12` float64, `1e-5` float32) on
**every** architecture.

## Performance — honest {#performance-honest}

Apple M-series (arm64, native), ns/op (lower is better); *simd* is this library,
*naive* is the textbook left-to-right loop (which the compiler already turns into
a pipelined scalar `FMADD`):

| op | n=8 | n=64 | n=512 | n=4096 |
|---|---|---|---|---|
| `Dot` float64 simd  | 7.6 | 14.3 | **71.7** | **539** |
| `Dot` float64 naive | 2.4 | 18.5 | 152 | 1075 |
| `Float32Dot` simd   | 9.5 | 11.7 | 39.4 | 276 |

The SIMD dot product is **~2× the compiler's scalar loop** on medium/large
vectors (≈57 GB/s float64, ≈59 GB/s float32 at n=512), and loses only on tiny
inputs (n ≤ 8) where unroll/setup overhead dominates.

amd64's AVX2+FMA kernel is correctness-validated on real x86 (an AVX2/FMA VM);
native throughput is pending (the x86 runner here is TCG-emulated).

**ppc64le — measured on real POWER9** (GCC Compile Farm cfarm433, Go 1.26.4,
2026-06-27): the **float32 VSX kernel runs ~1.55–1.61× over the gc-autovectorized
naive loop** for n ≥ 64 (POWER9-gated), so it is kept. For **float64**, however,
on real POWER9 the gc-autovectorized scalar loop *beats* the VSX kernel (VSX was
~0.82× at n ≥ 512), so **float64 honestly routes to that loop and ships no VSX
kernel** — measured, not assumed. s390x, riscv64 and loong64 stay
**QEMU-validated for correctness**, native perf pending real hardware.
