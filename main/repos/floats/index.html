floats

floats

SIMD-accelerated reductions over []float32 and []float64 — the dot product, sum, min, max, Euclidean (L2) distance and cosine similarity that sit at the heart of vector search, embeddings and numerics. Pure Go (CGO_ENABLED=0, stable Go, no GOEXPERIMENT). The hot reduction loops are real FMA SIMD on all six of Go’s 64-bit targets, assembly generated by go-asmgen. Repository →

API

For []float64 (top-level) and []float32 (the Float32* functions):

float64float32meaning
Dot(a, b)Float32Dot(a, b)a·b = Σ aᵢbᵢ
Sum(a)Float32Sum(a)Σ aᵢ
Min(a) / Max(a)Float32Min(a) / Float32Max(a)min / max (NaN-propagating)
Distance(a, b)Float32Distance(a, b)‖a−b‖₂ = √Σ(aᵢ−bᵢ)²
CosineSimilarity(a, b)Float32CosineSimilarity(a, b)a·b / (‖a‖₂‖b‖₂)
import "github.com/go-simd/floats"

sim := floats.CosineSimilarity(query, doc)  // []float64 relevance score
d   := floats.Float32Distance(embA, embB)   // []float32 L2 distance
dp  := floats.Dot(a, b)                      // a·b

Dot, Distance, CosineSimilarity require len(a) == len(b) and panic otherwise; Min/Max panic on an empty slice; Sum of empty is 0. The float32 dot/sum/squared-difference accumulate in float32; cosine and distance take the final square root in float64 for accuracy.

Elementwise updates (BLAS level 1)

Since v0.4.0, the float64 in-place updates behind iterative solvers (CG, GMRES), Householder QR and LU elimination:

functioncomputes
Axpy(alpha, x, y)y[i] = math.FMA(alpha, x[i], y[i]) (y += αx)
Xpby(x, beta, y)y[i] = math.FMA(beta, y[i], x[i]) (y = x + βy)
AxpyDot(alpha, x, y, w)Axpy, then returns Σ y[i]*w[i] over the updated y, in one pass
Scale(alpha, x)x[i] *= alpha
// one conjugate-gradient step
floats.Axpy(alpha, p, x)               // x += αp
rr := floats.AxpyDot(-alpha, ap, r, r) // r -= αAp, rr = r·r
floats.Xpby(r, rr/rrOld, p)            // p = r + βp

They operate on the first len(x) elements and panic if y (or w) is shorter; y may be the same slice as x or w. The updated slices are bit-identical to math.FMA on every architecture: one rounding per element, via VFMADD (amd64 AVX2+FMA), VFMLA/FMADDD (arm64 NEON) or the portable math.FMA loop (ppc64le, s390x, riscv64, loong64, where no kernel has been measured on silicon yet). AxpyDot’s returned sum is a lane-blocked reduction, like Dot.

Speedup over the hand-written scalar loop (y[i] += alpha*x[i], …), single core, median of 3:

Products, combinations, clamping, infinity norm

Since v0.5.0, the vector kernels of splitting solvers (ADMM / OSQP-style quadratic programming):

functioncomputes
Mul(dst, a, b)dst[i] = a[i]*b[i]
Axpby3(dst, alpha, a, beta, b, gamma, c)dst[i] = math.FMA(gamma, c[i], math.FMA(beta, b[i], alpha*a[i])) (αa + βb + γc, fused)
Clamp(dst, v, lo, hi)dst[i] = min(max(v[i], lo[i]), hi[i]) with the exact rules below
MaxAbs(v)the largest abs(v[i]) (∞-norm); 0 for an empty slice
floats.Axpby3(t, alpha, ax, 1-alpha, zPrev, 1, yOverRho)
floats.Clamp(z, t, l, u)
rNorm := floats.MaxAbs(r)

They work on the first len(a) (len(v)) elements, panic if another slice is shorter and let dst alias an input. Bit-identical on every architecture (NaN payloads of arithmetic results aside): Mul is one IEEE multiply; Axpby3 is fused, so it differs from the unfused expression by a few ULP of Σ|terms|; Clamp and MaxAbs round nothing.

Clamp is r := v; if lo > r { r = lo }; if hi < r { r = hi }: a NaN v passes through with its own bits (either sign), a NaN bound is ignored, lo > hi gives hi, signed zeros tie. MaxAbs returns math.NaN() if any element is NaN (either sign, quiet or signaling), +Inf if there is an infinity and no NaN, and +0 for an all-zero slice.

Kernels: AVX2+FMA on amd64 (VMULPD, VFMADD231PD, VMAXPD/VMINPD, VANDPD plus an unordered-compare NaN mask), NEON on arm64 (VFMUL, VFMLA, VFCMGT+VBIT, VFABS+VFMAX), the portable loops on ppc64le, s390x, riscv64 and loong64. Tested for every length 0..257 at four offsets with planted negative and signaling NaNs and signed zeros, at every position of 0..67, with guard pages and fuzzing, at 100% coverage on amd64 and arm64.

Unfused, NumPy-exact updates

Since v0.7.0:

functioncomputes (NumPy expression)
AxpyNoFMA(alpha, x, y)y[i] = y[i] + alpha*x[i]
XpbyNoFMA(x, beta, y)y[i] = x[i] + beta*y[i]
Axpby3NoFMA(dst, alpha, a, beta, b, gamma, c)alpha*a[i] + beta*b[i] + gamma*c[i], left to right
AxpyDiffNoFMA(dst, a, f, b, c)a[i] + f*(b[i] - c[i]), the differential-evolution mutation

Axpy, Xpby and Axpby3 are fused (one rounding), which NumPy never is: y + alpha*x is a multiply that rounds into a temporary and an add that rounds again. A solver validated by exact equality against SciPy needs that path, so these kernels round every product and every sum on its own, in the order NumPy evaluates the temporaries, and are bit-identical to the NumPy expression on every architecture (the payload of a NaN created by Inf - Inf or 0*Inf aside). amd64 uses VMULPD/VADDPD/VSUBPD, arm64 VFMUL/VFADD/VFSUB; the portable code puts every product behind a float64(...) conversion, which keeps the Go compiler from fusing it. dst may be the slice of an input (AxpyDiffNoFMA(b, b, f, x, b) is b += f*(x - b)).

Validated against NumPy 2.5.4 on 13 088 committed fixture cases (four kernels, ten value families including ±0, ±Inf, NaN of both signs and cancellation in b - c, every length 0..300 and block boundaries): 0 mismatches on arm64 and amd64. A planted fused variant and planted reordered variants are caught by the same fixture. Speedups over NumPy are not published yet: the benchmark (bench/numpycmp) refuses to run at a machine load of 8 or above.

Reproducing np.sum: SumPairwise

Since v0.6.0:

functioncomputes
SumPairwise(a)Σ a[i], bit-identical to np.sum(a) for a contiguous 1-D float64 array; +0 for an empty slice

Sum adds in the lane order of the SIMD kernels, which is fast but not NumPy’s order, so its last bits differ from np.sum. Use SumPairwise when a result must be reproducible against NumPy, for example a stopping test comparing np.std of a population with a tolerance. It is NumPy’s pairwise summation, transcribed from DOUBLE_pairwise_sum (numpy/_core/src/umath/loops_utils.h.src, v2.5.3): fewer than 8 elements are added left to right from -0; up to 128 elements are summed with eight independent accumulators folded as ((r0+r1)+(r2+r3)) + ((r4+r5)+(r6+r7)), then the non-multiple-of-8 rest is added one by one; a longer block is split at n/2 rounded down to a multiple of 8. np.add.reduce adds the result to its initial +0, so a slice holding only -0 sums to +0, as in NumPy.

It is bit-identical on every architecture: the order is fixed in the code, not by the width of a vector register, and no step is a fused multiply-add. Since v0.7.0 the 8..128-element blocks run in SIMD on amd64 (AVX2: the eight accumulators r[0..7] are two 4-lane registers) and arm64 (NEON: four 2-lane registers); every lane receives exactly the additions NumPy’s scalar code performs on its r[j], so the bits do not change. Other architectures run the portable Go block, which is also the test reference for the SIMD blocks.

Validated against NumPy 2.5.4 on 6 990 committed fixture cases (every length 0..300 for nine value families, both sides of every block boundary 128·2^j ± 12, and 1e5 / 1e6 / 2^20 with odd lengths): 0 mismatches. A NaN result is compared bit for bit when exactly one NaN enters the sum and the hardware keeps NaN payloads (RISC-V returns the canonical NaN, so only “is NaN” is compared there); with several NaNs, which one comes out is hardware-dependent in NumPy too. FuzzSumPairwise checks against an independent transcription; 100% coverage on every CI lane.

Why this library

This is the only pure-Go float reduction library that ships the full vector-search API (dot / Euclidean / cosine) for both float32 and float64 on all six of Go’s 64-bit SIMD architectures:

Algorithm & per-arch kernels

Every kernel is an FMA-based vectorised reduction: a multi-lane accumulator folded with a fused multiply-add at the vector stride, then a horizontal reduce and a scalar tail.

archISAFMA opnotes
amd64AVX2 + FMA3VFMADD231P{S,D}gated on cpu.X86.HasAVX2 && HasFMA; scalar fallback otherwise
arm64NEONVFMLA4 accumulators, ×4 unroll for ILP; baseline
riscv64RVVVFMUL+VFREDOSUMVSlength-agnostic VSETVLI stripmining; gated on cpu.RISCV64.HasV
s390xvector facility (big-endian)VFMADBfloat64 vectorised; float32 uses scalar (no .SB ops in assembler); z13 baseline
ppc64leVSX (float32 only)XVMADDASPXV* ops WORD-encoded; POWER9-gated. float64 has no VSX kernel — on real POWER9 the gc-autovectorized scalar loop beats VSX, so float64 routes to that loop
loong64LSXvfmadd.d/vfmadd.sLSX FP ops WORD-encoded; LA464 baseline

Floating-point determinism

A SIMD reduction does not add terms left-to-right: it keeps several independent accumulator lanes (for ILP) and folds them at the end, so its rounding differs from a naïve scalar loop. For dot / distance / cosine, bit-exactness against a naïve loop is neither meaningful nor required — correctness to a few ULP is. The reference the tests and fuzzers check against (dotLanes, sumSqDiffLanes, …) reduces in the same lane-blocked order the kernels use, and each kernel must match it to a tight, documented tolerance (1e-12 float64, 1e-5 float32) on every architecture.

Performance — honest

Apple M-series (arm64, native), ns/op (lower is better); simd is this library, naive is the textbook left-to-right loop (which the compiler already turns into a pipelined scalar FMADD):

opn=8n=64n=512n=4096
Dot float64 simd7.614.371.7539
Dot float64 naive2.418.51521075
Float32Dot simd9.511.739.4276

The SIMD dot product is ~2× the compiler’s scalar loop on medium/large vectors (≈57 GB/s float64, ≈59 GB/s float32 at n=512), and loses only on tiny inputs (n ≤ 8) where unroll/setup overhead dominates.

amd64’s AVX2+FMA kernel is correctness-validated on real x86 (an AVX2/FMA VM); native throughput is pending (the x86 runner here is TCG-emulated).

ppc64le — measured on real POWER9 (GCC Compile Farm cfarm433, Go 1.26.4, 2026-06-27): the float32 VSX kernel runs ~1.55–1.61× over the gc-autovectorized naive loop for n ≥ 64 (POWER9-gated), so it is kept. For float64, however, on real POWER9 the gc-autovectorized scalar loop beats the VSX kernel (VSX was ~0.82× at n ≥ 512), so float64 honestly routes to that loop and ships no VSX kernel — measured, not assumed. s390x, riscv64 and loong64 stay QEMU-validated for correctness, native perf pending real hardware.

Coverage

All six arches validated in CI — amd64/arm64 natively, the other four under QEMU (tonistiigi/binfmt) — at 100% test coverage, with differential tests and FuzzDot/FuzzDistance/FuzzAxpy against the scalar reference on every architecture; the elementwise kernels also run against PROT_NONE guard pages on both sides of every slice.
